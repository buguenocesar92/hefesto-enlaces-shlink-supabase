# Preparar Supabase
1. Crear un proyecto EXCLUSIVO para Shlink. No usar la base que ya aloja Hefesto, KraftDo u otra app. El kit usa public y no migra ni protege tablas ajenas. Admite PostgreSQL 16/17; otras versiones requieren nueva validación y cliente pg_dump compatible.
2. Desactivar Data API para este proyecto desde sus ajustes. Este kit usa conexión PostgreSQL y no necesita REST/GraphQL público. Ejecutar sql/01-supabase-app.sql con el rol administrativo de Supabase. Rechaza public con tablas existentes; crea shlink_app sin privilegios administrativos y revoca acceso de anon/authenticated a objetos nuevos de ese rol.
3. Asignar al rol la POSTGRES_PASSWORD generada en .env mediante una sesión administrativa de psql con TLS y `\password shlink_app` (entrada interactiva). No incluir la clave en un ticket ni sustituirla dentro de SQL pegado al historial del editor. La clave debe coincidir exactamente.
4. En los ajustes de conexión tomar el host directo puerto 5432, o Session pooler puerto 5432 si el VPS no tiene IPv6. NO Transaction pooler puerto 6543. Con conexión directa POSTGRES_USERNAME=shlink_app. Con Session pooler usar el formato de usuario específico de tu proyecto para ese rol (normalmente shlink_app.REFERENCIA); current_user dentro de PostgreSQL debe ser shlink_app. Confirmar que el pooler admite ese rol.
5. Guardar la CA correspondiente al endpoint en certs/ca.crt. Verificar hostname y cadena; no cambiar a require ni aceptar certificados inválidos para sortear errores. Configurar POSTGRES_HOST sin protocolo/puerto, permisos de red y variables SUPABASE_DEDICATED_CONFIRMED=true y SUPABASE_DATA_API_DISABLED=true solo tras completar pasos.
6. `docker compose run --rm preflight` valida CA, conexión, versión, rol, permisos y tablas. El chequeo no comprueba remotamente el interruptor Data API: la variable registra tu confirmación y la SQL comprueba permisos relevantes.
7. El arranque PHP verifica la configuración de Doctrine, conecta por PDO con verify-full y exige rol shlink_app/TLS. Después el instalador nativo ejecuta migraciones. No hay usuario postgres en el contenedor de Shlink.

## TLS del kit
DB_USE_ENCRYPTION de Shlink configura por defecto un modo permisivo. Aquí esa opción se deja false y se reemplaza explícitamente mediante config/autoload/zz-hefesto.global.php con sslmode=verify-full y sslrootcert en el nivel de conexión de Doctrine. PGSSLMODE/PGSSLROOTCERT refuerzan la misma política para libpq y dbtools. False en esa variable no significa que este kit conecte sin TLS. No retirar el archivo de configuración adicional.

Usar una sola instancia inicialmente y limitar workers. Medir conexiones y latencia; la caída/pausa de Supabase afecta redirecciones. Dimensionar y contratar disponibilidad según el servicio que se venda. No se incluye una base local de respaldo en caliente.
