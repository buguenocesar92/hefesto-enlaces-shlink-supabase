# Coolify y primera campaña
1. Elegir dominio corto (go.tudominio.cl) y panel (enlaces.tudominio.cl) distintos. Usar proyecto Supabase, rol y despliegue separados por cliente. Asignar CPU/RAM según pruebas; el kit parte con 2 workers web y 1 de tareas, no con capacidad garantizada.
2. Preparar .env/CA, preflight y bootstrap privado del README. No añadir dominios públicos de Coolify durante bootstrap. El instalador genera INITIAL_API_KEY solo si no hay otras claves; cambiarla en .env o quitarla no revoca la ya guardada.
3. En el panel añadir el servidor y clave manualmente. Nunca configurar SHLINK_SERVER_API_KEY ni publicar un servers.json con claves: el panel es estático y esos datos quedarían descargables. La configuración manual se guarda en el navegador; no usar equipos compartidos. No hay login de usuario/password en este panel.
4. Cerrar bootstrap: `docker compose -f compose.yaml up -d --force-recreate app panel`. Confirmar que los puertos host 8092/8093 desaparecieron. Guardar la clave inicial en un gestor y retirarla de .env cuando se reemplace por claves individuales. Para crear claves usar `docker compose exec app shlink api-key:generate --help`, elegir nombre/alcance/vencimiento apropiados y guardar el resultado. Revocar claves mediante CLI tras consultar su ayuda; no confundir edición del .env con revocación.
5. Coolify: cargar el directorio como Compose, permitir build del Dockerfile, configurar variables y montar certs/ca.crt + ops necesarios para preflight. Asociar dominio corto al servicio app:8080 y dominio panel a panel:8080 con HTTPS. No usar el override bootstrap. No escalar sin revisar conexiones, locks y tareas; Redis no está incluido.
6. Configurar TRUSTED_PROXIES con IP/CIDR concreto del proxy. Preservar Host, descartar cabeceras falsificadas y mantener CORS restringido al origen HTTPS del panel. CORS no sustituye autenticación API. Agregar protección de acceso al panel si el cliente la requiere, sin bloquear las redirecciones públicas.
7. Registrar en el panel el servidor https://go.tudominio.cl y la clave correspondiente. Crear un enlace de ensayo, visitar desde otro dispositivo, editar destino y comprobar que redirige al nuevo. El código 302 evita fijar permanentemente destinos en cachés; revisar también CDN/proxy y no cachear rutas /rest de administración.
8. Probar un QR que codifique la URL corta con tu herramienta elegida. Cambiar el destino mantiene el QR solo si conservas el mismo dominio y slug.

IP/referrer/user agent y visitas huérfanas desactivados en el kit. Se conserva conteo de visitas; no equivale a personas únicas ni conversiones. Sin GeoLite no hay ubicación geográfica. Revisar logs del proxy, retención y políticas del cliente antes de anunciar anonimato o cumplimiento legal. No hay Matomo, Redis, Mercure o RabbitMQ conectados.
